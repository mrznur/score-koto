# Goal API pass-through proxy rearchitecture

The football data path is rebuilt as a stateless Goal API proxy: every football read endpoint now calls Goal API directly on each request, with no database storage, no multi-provider merge layer, and no football sync crons. The four secondary football providers (API-Football, football-data.org, TheSportsDB) and the `FootballProviderManager` are deleted, the `FootballMatch` Prisma model is removed, and `FootballService` no longer touches `PrismaService`. `SyncService` is gutted to two jobs — a football live-push timer (Goal API → WebSocket every 2 min, no DB writes) and the unchanged cricket sync. Cricket is untouched end to end. The frontend is re-pointed at the Goal API fixture id as the single match identifier, FixturesScreen drops its 2-minute polling for load-on-mount plus pull-to-refresh, and LiveScreen filters to live-only. All four docs are rewritten to match.

**Watch for:** none blocking. One non-blocking housekeeping item: `backend/src/football/match-identity.ts` is now an orphan (no importer) but is intentionally retained; it compiles standalone and is harmless.

**Verdict**: APPROVED

## High-level view

Goal API is now the sole football provider and the only football data store is Goal API itself. `FootballService` became a thin pass-through — its read methods call `GoalApiProvider` and return normalized rows directly, deduping the live endpoint's live-plus-results merge by `id`. The `id` on every normalized match equals the Goal API fixture id (`goalApiId`), which is the contract the rest of the system rides on: the frontend's React keys, `dedupeMatches`, `sameMatch`, and match-detail navigation all use it, and `/football/matches/:id` treats that id as the Goal API fixture id to fan out events/stats/lineups/commentary in parallel.

The sync layer collapsed from five crons to two. The football today/results/upcoming jobs are gone because there is nothing to persist; the remaining `*/2` football job fetches Goal API live data and pushes it over the WebSocket with no DB write. Cricket keeps its `*/5` cron and DB persistence exactly as before. This directly serves the original real-time-consistency goal: every screen reading football pulls the same Goal API data on demand, and the live push keeps the home carousel, live page, and match detail in step.

The frontend changes are small and targeted. FixturesScreen removed its `setInterval` polling and `selectedDateRef`, keeping only mount-load and a pull-to-refresh `RefreshControl`. LiveScreen swapped `fixEarlyLive` for `cleanLive` in both its REST load and its WebSocket `onFootballUpdate` so the live page shows only truly live matches even though `/football/live` returns recently-finished matches too. HomeScreen dropped a DEV-only debug log; its live path already filtered through `cleanLive` and now receives fresh Goal API pushes. The `FootballMatch` interface makes `goalApiId` required and `getMatch` takes a `goalApiId` parameter, matching the backend's `id = goalApiId` invariant.

Docs (ARCHITECTURE, API_PROVIDERS, DEVELOPMENT, PROGRESS) describe the proxy architecture, the two-cron schedule, the single Goal API football provider, the removed football sync POST routes, and the env-var contraction. No code was touched in the docs commit; the backend build and frontend typecheck both still pass.

### Goal API as single source of truth for football

The merge layer is gone: `ProvidersModule` registers and exports only `GoalApiProvider` and `CricketProviderManager`, and a search across `backend/src` finds no remaining import or reference to any deleted provider (`ApiFootballProvider`, `FootballDataProvider`, `TheSportsDbProvider`, `FootballProviderManager`). One behavioral consequence worth stating plainly: `/football/live` merges Goal API `/fixtures/live` with `/results/today` and dedupes by `id`, so it can include recently-finished matches — which is exactly why the frontend filters the live page with `cleanLive`.

### The `id === goalApiId` invariant

`GoalApiProvider.normalize()` sets both `id: f.id` and `goalApiId: f.id`, and all four read paths (`getLive`, `getByDate`, `getResultsToday`, `getFixtureNormalized`) flow through `normalize()`, so the invariant holds on every list row and on the match-detail `match` object. The `NormalizedFootballMatch` interface gained `id` and `lastSyncedAt` to match the frontend contract; `api.ts` makes `goalApiId` required and `getMatch` takes a `goalApiId` param, and navigation passes `m.id`. This is the lock-step contract the whole rearchitecture rides on.

### Cricket untouched

The diff touches no file under `backend/src/cricket/` and does not modify `cricket-provider.manager.ts`; `CricketService`, `CricketController`, `CricketModule`, and the `*/5` cricket cron (throttled to 30 min when idle) are byte-for-byte unchanged. `CricketMatch`, `CricketScorecard`, `SyncLog`, and `ApiUsage` Prisma models are retained so cricket sync, sync logging, and `QuotaService`/`QuotaModule` still compile.

### Frontend data-flow updates

FixturesScreen has no `setInterval` and no `selectedDateRef` (confirmed by search); it loads on mount and on pull-to-refresh only. LiveScreen applies `cleanLive` in both its REST `load` and its WebSocket `onFootballUpdate`, so the live page cannot show finished matches even though `/football/live` returns them. HomeScreen's live path already filtered through `cleanLive`; its `onFootballUpdate` re-filters incoming pushes, and the carousel is built from `buildFeatured(liveFootball, nearbyFootball, ...)` where `liveFootball` is `cleanLive`-filtered — the path that closes the original "home carousel not real-time" gap, since the `*/2` push now carries fresh Goal API live data.

### Test coverage

No automated tests were added or run in this branch; verification rests on the build, the typecheck, and structural grep checks. Not covered by automated tests: the live WebSocket push delivering fresh Goal API data to connected clients, and `/football/matches/:id` correctly fanning out events/statistics/lineups/commentary for a real fixture id. Both are worth end-to-end coverage in a follow-up.
